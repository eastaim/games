# ADR-001. 포털은 게임을 iframe으로 띄운다

- 상태: 채택
- 날짜: 2026-09-12

## 맥락

게임 여러 개를 한 페이지에서 고르고 실행해야 한다. 게임들은 이미 각자 저장소에서
Vite + Phaser로 빌드되어 각자 GitHub Pages 주소로 배포되어 있다.

## 검토한 선택지

### A. 모노레포 통합

포털 저장소 안에 게임 소스를 모으고, 목록에서 고르면 `dynamic import`로 해당 게임 모듈만
불러와 같은 페이지에 마운트한다.

- 장점: 진짜 단일 페이지. Phaser 번들을 게임끼리 공유하므로 두 번째 게임부터 로딩이 빠르다.
  공통 UI·점수 저장 코드를 한 번만 쓴다.
- 단점: 기존 게임을 전부 이 저장소로 옮겨야 한다. 게임 하나의 빌드 실패가 포털 전체 배포를
  막는다. 게임마다 독립된 이력과 배포를 잃는다.

### B. 포털 + iframe (채택)

게임은 지금처럼 각자 저장소·각자 배포를 유지한다. 포털은 목록만 보여주고,
고른 게임의 URL을 iframe으로 띄운다.

- 장점: **마이그레이션이 없다.** 게임 저장소를 한 줄도 고치지 않는다. 게임 하나가 깨져도
  포털과 다른 게임은 멀쩡하다. 게임은 계속 독립적으로 개발·배포된다.
  새 게임 추가 비용이 레지스트리 항목 하나다.
- 단점: 게임마다 Phaser를 따로 받으므로 첫 로딩이 느리다(게임당 약 1.2MB).
  포털의 테마가 게임 내부까지 미치지 않는다. iframe 안팎의 포커스를 직접 챙겨야 한다.

### C. 모노레포 + 게임별 독립 페이지

한 저장소에서 Vite 멀티페이지로 빌드하고, 목록에서 `/games/mergedrop/`으로 이동한다.

- A의 마이그레이션 비용을 그대로 치르면서 SPA 이점은 얻지 못한다. 탈락.

## 결정

**B를 택한다.**

결정적인 이유는 **게임 개발 속도를 포털이 늦추지 않는 것**이다. 포털은 게임을 보여주려고
만드는 것이지, 게임 개발에 새 제약을 걸려고 만드는 것이 아니다. A는 게임 하나를 만들 때마다
포털 저장소를 거치게 만들고, 그 순간 포털이 짐이 된다.

첫 로딩 속도는 실제로 치르는 대가다. 게임 하나를 고르면 Phaser를 새로 받는다.
다만 포털 자체가 3.5KB(gzip)이라 목록은 즉시 뜨고, 로딩은 고른 게임 하나에만 발생한다.

## 이 결정이 가능하게 한 것

포털과 게임이 **같은 오리진**(`y3games.github.io`)에 있다는 점이 iframe 방식의 약점 하나를
없앴다. localStorage가 공유되므로 포털이 게임의 최고 점수를 게임 수정 없이 직접 읽는다.
게임을 다른 도메인에 올렸다면 점수 표시는 `postMessage` 없이는 불가능했을 것이다.

## 되돌릴 때

게임 수가 늘어 첫 로딩이 문제가 되면 A로 옮길 수 있다. 그때 버려지는 것은
`src/ui/GameView.ts` 하나뿐이다. 레지스트리(`src/catalog/`), 라우팅, 점수, 테마, 카드 UI는
`path`를 모듈 로더로 바꾸는 것 외에 그대로 쓴다.
